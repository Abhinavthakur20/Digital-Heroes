- **Next.js (App Router)** — single deployable app, API routes double as backend, fast to scaffold.

- **Stripe (test mode)** — Checkout for monthly/yearly plans, webhook flips subscription status. Test mode satisfies "PCI-compliant provider" without needing real money.
- **Tailwind CSS** — fastest path to a clean, non-golf-cliché look under time pressure.
- **Vercel** — deploy target per PRD, new account as required.

## 6. Draw & Prize Pool Logic (core algorithm)

**Entry generation:** each active subscriber gets one 5-number ticket per monthly draw.
- *Random mode:* uniform random 5 numbers from a fixed range (e.g. 1–49).
- *Algorithmic mode:* biases number selection using the subscriber's recent score frequency (documented as a simple, explainable heuristic — not a black box).

**Pool calculation (per draw):**
```
total_pool = active_subscriber_count × avg_subscription_fee × prize_pool_share
pool_5 = total_pool × 0.40  (+ any rolled-over jackpot)
pool_4 = total_pool × 0.35
pool_3 = total_pool × 0.25
```
- If multiple winners share a tier, split that tier's pool equally.
- If nobody hits 5 numbers, `pool_5` rolls into next month's jackpot.

**Simulation before publish:** run the exact same matching logic against current entries without writing `winners` rows or changing `payment_status` — show admin the would-be results first.

## 7. Documented Assumptions (ambiguity the PRD leaves open)

State these explicitly in the README — this is what "problem-solving" is graded on:

1. **How entries are created** — PRD doesn't specify if users pick numbers or numbers are assigned. Assumption: auto-assigned per active subscriber per month (no manual number picking), since PRD frames scores/charity as the user-facing actions, not a numbers game.
2. **Prize pool base** — "portion of subscription fee" isn't given a fixed platform-wide %. Assumption: a configurable `prize_pool_share` (e.g. 20% of fees) admins can adjust, so the 40/35/25 split is applied to that share, not the whole fee.
3. **Charity % vs. prize pool %** — treated as two independent allocations of the subscription fee (charity ≥10%, prize pool fixed %), not competing for the same slice.
4. **"Algorithmic" draw weighting** — defined narrowly as score-frequency bias rather than a full statistical model, kept simple and explainable within the timeline.
